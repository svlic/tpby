# 待修改功能与风险清单

本文依据 [ADR](adr/README.md)、当前代码和 2026-09-27 的维护者确认整理，并明确区分已完成对齐、尚未完成的工作和已知风险。

## 已完成的 P0 对齐

以下偏差已于 2026-09-27 修复并由自动化测试覆盖：

- **F-001：SOURCE 搜索与二层校验。** 现在只搜索带引号的裸六位 code，并在本地验证“编号”字段、code 边界、对象数量和唯一验证视频。
- **F-002：有限请求级重试。** Reader/Writer 显式配置 Telethon 请求与连接重试；确定性 `AmbiguousSourceError` 不重试，最终异常进入 failure。没有在业务层盲目重放完整 task。
- **F-003：固定 180 天日期窗口。** 已用固定 timedelta 替代六个日历月，并增加可区分两种算法的边界测试。

## 待修改功能

### P1：降低状态损坏和运维风险

#### F-004：为跨 SQLite/Telegram 的半完成操作提供 reconciliation

- **问题场景：** 新 Telegram 消息已经发出，但进程在写 message index 或激活 group 前退出，会留下无法由数据库识别的消息。
- **方向：** 明确可恢复操作阶段，或增加启动时/人工执行的对账命令。删除旧消息失败导致重复内容已被接受，不应因此删除新内容。
- **关联：** ADR-005。

#### F-005：让 rebuild 在写入失败时保留旧数据库

- **现状：** 频道扫描完成后先提交数据库清空，再开始重建写入；后续写入失败可能留下空或不完整数据库。
- **方向：** 在临时数据库中完成 schema、数据和基本校验，再通过受控替换切换；同时保留失败诊断。
- **兼容要求：** 对 metadata 未知字段保持宽容，只要 `hashes` 可读取就恢复。
- **关联：** ADR-008。

#### F-006：提供明确的 failure 查看与重放入口

- **现状：** README 要求人工删除 `failures` 行后重新投递消息。
- **方向：** 至少提供只读列出、按消息清除/重放的 CLI，并保留原因和重试结果，避免直接操作 SQLite 成为常规流程。
- **关联：** ADR-007。

### P2：容量增长后再实施

#### F-007：评估安全并行边界

- **现状：** 单个 `asyncio.Lock` 串行执行全部业务操作。
- **方向：** 优先考虑并行搜索、下载和哈希计算，继续串行化可能修改相同 logical group 的阶段；在没有冲突模型前不应直接移除全局锁。
- **触发条件：** 实际队列延迟或吞吐不能满足需求。

#### F-008：增加媒体垃圾回收

- **现状：** 媒体进入 UP/BLACKLIST 或 group 失活后仍保留本地文件。
- **方向：** 根据所有可恢复引用计算候选文件，先提供 dry-run 和保留期，再允许删除。
- **触发条件：** 磁盘增长成为实际成本问题。

#### F-009：基于约 10 万 hash 做性能基准

- **关注点：** `connected_groups()` 迭代执行查询并逐组加载媒体；大连通分量会增加查询和重新上传成本。
- **方向：** 构造接近真实分布的数据，而不是只测 10 万个互不关联 hash，再决定是否增加索引、递归查询或缓存。

#### F-010：固定构建输入

- **现状：** Python 依赖仅使用版本范围，基础镜像未固定 digest。
- **方向：** 在需要可重复发布时增加 lockfile、依赖哈希和基础镜像更新流程。

## 风险登记

| ID | 风险 | 影响 | 当前处理/接受程度 |
| --- | --- | --- | --- |
| R-001 | Telegram 上传成功、SQLite 提交前崩溃 | 孤儿消息、重复发送、本地与频道漂移 | 高；尚无 reconciliation，见 F-004 |
| R-002 | rebuild 清空数据库后写入失败 | 本地状态为空或不完整 | 高；见 F-005 |
| R-006 | 没有真实 Telegram 端到端测试 | forward metadata、album、删除事件和部分 RPC 行为未经验证 | 高；首次生产前应做受控频道演练 |
| R-007 | 全局锁限制吞吐 | 高峰期事件积压 | 未知；有指标后处理，见 F-007 |
| R-008 | 大 logical group 的闭包查询与全量重发 | 延迟、Telegram 调用和带宽成本上升 | 未量化；见 F-009 |
| R-009 | 媒体文件不清理 | 磁盘持续增长 | 已知且暂时接受；见 F-008 |
| R-010 | 停机期间遗漏 UP 删除事件 | hidden 未记录，媒体未来可能重新出现 | 维护者明确接受 |
| R-011 | 数据库丢失后 hidden/DEAL/failure/bypass 不恢复 | 展示和处理历史变化 | ADR-008 明确接受的恢复边界 |
| R-012 | 两个独立 UP 使用完全相同 code list | rebuild 错误合并 logical group | 暂时假定不会发生 |
| R-013 | 宽容读取未知 metadata | 格式语义变化时可能误读 hashes | 接受向前兼容；发布新版本时必须保持 `hashes` 语义 |
| R-014 | 依赖和基础镜像未锁定 | 重建不可完全复现、供应链变化 | 中低；见 F-010 |

## 已关闭风险

- **R-003：** 搜索和二层校验与 ADR-004 不一致——由 F-001 关闭。
- **R-004：** 瞬时 Telegram 请求第一次失败就固化为 failure——由 F-002 关闭；重试耗尽后进入 failure 是预期行为。
- **R-005：** 日期边界使用六个日历月——由 F-003 关闭。

## 已接受而无需立即修复的限制

- 删除旧 Telegram 消息失败时允许旧、新内容并存。
- hidden 只在当前数据库生命周期内有效。
- 停机期间的 UP 删除事件无需补扫。
- 相同字节但扩展名或 MIME 不同的文件按同一 SHA-256 复用。
- 当前只支持单机、单服务实例。
- 暂时假定 rebuild 不会遇到两个 code list 完全相同但独立的 UP group。
