# ADR-002：使用 SQLite 与按 SHA-256 寻址的媒体文件

- 状态：已接受（回溯记录）
- 决策时间：约 2026-09-27
- 相关提交：`0fdf085`、`6ac39dc`

## 背景

服务需要长期保存 task、媒体关系、logical group、Telegram 消息索引、blacklist、hidden、failure 和 bypass。媒体本身可能较大，同一文件也可能出现在多个 task 中。预期媒体 hash 数量约为 10 万，不需要多机共享数据库。

## 决策

- 使用单机 SQLite 保存结构化业务状态，并启用 foreign keys 和 WAL。
- 媒体文件保存在文件系统，实际文件字节的 SHA-256 是媒体身份。
- 文件按 SHA-256 命名和复用；SQLite 保存路径、MIME 和 task-media 关系。
- task 与 media 建模为多对多关系，logical group 单独保存并保留活动状态。
- SHA-256 分块计算，并移到工作线程以避免阻塞 asyncio 事件循环。
- 相同内容即使扩展名或 MIME 不同也可以复用同一个文件；该情况预计极少发生。

## 结果

- 避免将大对象写入 SQLite，并减少重复媒体的磁盘占用。
- 数据库和媒体目录共同构成完整本地状态。
- 当前优先保留可恢复性，不主动清理已无活动引用的文件。
- 未来可以增加按数据库引用执行的媒体垃圾回收，但不属于当前决策。

## 证据与边界

- **事实：** schema、WAL、索引和文件存储实现在 `repository.py` 与 `telegram.py`。
- **事实：** SHA-256 身份规则来自原始业务要求。
- **事实：** 维护者确认约 10 万 hash、单机运行，并接受内容相同文件复用。
- **推断：** 10 万量级下现有查询应先用实际数据测量，再决定是否改用其他数据库。
- **开放项：** 尚无生产数据上的容量和查询性能基准。
