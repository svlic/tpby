# ADR-005：使用 staged group 缓解跨系统非原子更新

- 状态：已接受（回溯记录）
- 决策时间：约 2026-09-27
- 相关提交：`0fdf085`、`6ac39dc`

## 背景

SQLite 事务不能与 Telegram 上传、删除 RPC 组成原子事务。组归并时既要创建新频道内容，又要替换本地 active group 并删除旧内容。

早期实现先停用旧组再上传新组；这会在上传失败时失去原有活动状态，因此未作为最终方案保留。

## 决策

- 先在 SQLite 创建 `active=false` 的 staged group。
- 完整发布新组并记录 Telegram message index。
- 发布成功后再激活新组、停用旧组，然后删除旧 Telegram 消息。
- 发布失败时清除 staged group 和本次新 task，旧组保持 active。
- 程序删除旧 UP 消息前先移除其 index，避免删除事件被误判为人工隐藏。
- 可能修改 logical group 的决策、发布、激活和删除使用单个 mutation lock 串行化；只读搜索、媒体下载和 hash 在锁外受控并行。
- 删除旧 Telegram 消息失败时允许旧、新内容同时存在；不能以删除成功为代价回滚已经发布的新组。

## 结果

- 新组发布失败不会提前破坏旧活动组。
- 该顺序降低数据丢失风险，但不提供跨系统强一致性。
- 上传成功但本地索引提交前崩溃，仍可能产生 Telegram 孤儿消息。
- 激活成功但删除失败时会产生重复内容，这是已接受的降级结果。
- 准备阶段并行降低下载和搜索造成的队首阻塞；写入阶段继续串行，避免 hash 连通任务竞争。

## 证据与边界

- **事实：** staged publish、失败清理和串行 mutation 边界均存在于当前实现。
- **事实：** 开发线程记录了从“先停用旧组”到“先发布新组”的调整。
- **事实：** 维护者接受删除失败导致重复内容。
- **开放项：** 崩溃恢复和自动 reconciliation 尚未设计，未来可能需要。
- **后续演进：** 2026-09-27 已增加持久化 CODE job、并行准备和 Reader/Writer 自适应 I/O 门控；没有改变跨系统写入的串行一致性边界。
